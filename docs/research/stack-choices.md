# botpit stack research — auth, RBAC, rate limit, flags, queue, metrics, frontend, websockets

Date: 2026-09-12. Constraints from DECISIONS.md §2/§11/§14/§15 and docs/{roles-and-permissions,capacity-and-queueing,rooms}.md:
real accounts + JWT, many-to-many roles/permissions checked via `require_permission()` (HTTP and websocket),
per-account chat rate limit, FIFO join queue with position feedback + auto seat offer, Redis already required,
Prometheus `/metrics`, one small VPS later, local-first now. Bias throughout: fewest dependencies that are alive in 2026.

## 1. Auth

**Pick: hand-rolled — `pyjwt` + `pwdlib[argon2]` + own `users` table.**
- `fastapi-users` v15.0.5 (2026-03-27) is officially in **maintenance mode** since v15.0.1 (2025-10-25): "no new features", maintainers building a successor toolkit. Adopting a frozen library for the auth core of a new project is the wrong bet. https://github.com/fastapi-users/fastapi-users/releases · https://github.com/fastapi-users/fastapi-users
- It does support SQLAlchemy 2.0 async (`fastapi-users-db-sqlalchemy`, `AsyncSession`), but its `User` model is its own declarative mixin, its routers own `/register`, `/login`, `/users/me`, and role checks are "add a field + write a dependency" anyway. A many-to-many roles table would sit beside it, not inside it — you'd write `require_permission()` yourself regardless. https://fastapi-users.github.io/fastapi-users/latest/configuration/databases/sqlalchemy/
- Hashing: `passlib` last release 1.7.4 (2020-10-08), breaks on modern `bcrypt`/Python 3.13; FastAPI's own discussion recommends moving off it. `pwdlib` 0.3.1 (2026-08-12, `PasswordHash.recommended()` = Argon2id) wraps `argon2-cffi` 25.1.0 (2025-06-03). Use `pwdlib` for the tiny API and rehash-on-login support; `argon2-cffi` direct is the equally fine zero-abstraction alternative. https://github.com/fastapi/fastapi/discussions/11773 · https://pypi.org/project/pwdlib/ · https://pypi.org/project/passlib/ · https://pypi.org/project/argon2-cffi/
- JWT: `PyJWT` 2.14.0 (2026-09-11), HS256 with a settings secret. ~40 lines: `create_access_token`, `decode`, `get_current_user` dependency. https://pypi.org/project/PyJWT/
- Runner-up: `fastapi-users`. Why not: maintenance mode; forces its user model + router shapes; saves maybe a day now, costs every time roles/rooms need to touch the user row.

**Token strategy (websocket-heavy):**
- Access JWT, short (15 min), carried as `Authorization: Bearer` for HTTP. Refresh token = opaque random 32 bytes, stored hashed in a `refresh_tokens` table (user_id, hash, expires_at, revoked), delivered as `HttpOnly; Secure; SameSite=Strict` cookie scoped to `/auth/refresh`. Gives logout/revocation; JWT alone cannot be revoked (fastapi-users docs say so explicitly). https://fastapi-users.github.io/fastapi-users/latest/configuration/authentication/strategies/jwt/
- Websocket handshake: browsers cannot set headers on `new WebSocket()`. Three options: (a) `?token=` query param — leaks into proxy/access logs; (b) cookie — works only same-site and the SameSite/CSRF story for WS is muddy; (c) **first message**: `accept()`, then `await asyncio.wait_for(ws.receive_json(), 5)` expecting `{"type":"auth","token":...}`, else `close(4001)`. Pick **(c)**, with the access JWT (no dedicated WS token needed). It never touches logs, works for the same-box static frontend and for any future non-browser client, and one `ws_authenticate(ws) -> User` helper replaces `Depends`. Sources: https://dev.to/kaushikcoderpy/fastapi-websockets-async-connections-scaling-the-multi-worker-nightmare-2026-3346 · https://websocket.org/guides/frameworks/fastapi/ · https://oneuptime.com/blog/post/2026-01-24-websocket-authentication/view
- Don't smuggle the token via `Sec-WebSocket-Protocol`; it works but is a documented hack and Chrome requires echoing a subprotocol back. https://blog.openreplay.com/websocket-authentication/
- On access-token expiry mid-session: server closes with `4001` (see §8); client refreshes over HTTP and reconnects. Simpler than in-band re-auth.

## 2. RBAC

**Pick: hand-built schema + `require_permission()` dependency.**
- Needed model is small and fixed: `users`, `roles`, `permissions`, `user_roles`, `role_permissions`, plus `room_roles(room_id, user_id, role_id)` for the room-scoped moderator. That is five tables and one query: "permissions of user U, globally or in room R". Casbin's whole value (policy language, ABAC, deny-override, domains/tenants) is unused surface here.
- `pycasbin` is alive (1.43.0, 2025-05-10, 3 open issues) and `casbin-async-sqlalchemy-adapter` 1.17.0 (2025-12-10) works with `AsyncEnforcer`, but: policies live in a separate `casbin_rule` table that must be kept in sync with your users/rooms rows; `AsyncEnforcer` keeps policy in process memory and needs `load_policy()`/watcher for multi-worker consistency; `fastapi-authz` integration is sync-only and last released 2024-03-29. https://pypi.org/project/casbin/ · https://pypi.org/project/casbin-async-sqlalchemy-adapter/ · https://pypi.org/project/fastapi-authz/ · https://github.com/casbin/pycasbin
- Websocket gating: same function, not a `Depends`. `perms = await load_permissions(session, user_id, room_id)` once at subscribe time, store the frozenset on the connection object, check `"room:view_seat_detail" in conn.perms` when routing each event. Re-load on a Redis `perms_changed:{user_id}` event if live revocation matters (v2).
- Implementation sketch: `require_permission(name: str)` returns a dependency that takes `user: CurrentUser` and optional `room_id` path param, runs one SELECT over the join (cache per request), raises 403. Seed the default roles (`admin`, `player`, `spectator`, `moderator`) in an Alembic data migration.
- Runner-up: pycasbin + async adapter. Why not: second source of truth for the same facts, in-memory policy cache to invalidate across workers, RBAC-with-domains config to learn for what is one extra table.

## 3. Per-account rate limiting

**Pick: hand-rolled sliding-window Lua script on redis-py (`redis` 8.1.0, 2026-07-30), one `check_rate(key, limit, window) -> (allowed, retry_after)` used by both an HTTP dependency and the websocket chat handler.**
- `slowapi` 0.1.10 (2026-06-13, previous release Feb 2024): keyed by any `key_func`, Redis via `limits`, but **"websocket endpoints are not supported yet"** and it requires `request: Request` in every signature. Chat is the primary limit target and chat is on the websocket — disqualifying. https://pypi.org/project/slowapi/ · https://github.com/laurentS/slowapi
- `fastapi-limiter` 0.2.0 (2026-02-06, previous 2024-01): rewritten on `pyrate-limiter` 4.5.0 (2026-08-30, sliding-window-log, async Redis), has `WebSocketRateLimiter` and a custom `identifier` callable. Viable, but 30 open issues, one release in two years, and the whole feature is ~30 lines of Lua + 15 lines of Python. https://pypi.org/project/fastapi-limiter/ · https://github.com/long2ice/fastapi-limiter · https://pypi.org/project/pyrate-limiter/
- Sliding window log in Lua (ZADD now, ZREMRANGEBYSCORE < now-window, ZCARD, EXPIRE) is atomic and per-key; key = `rl:{scope}:{user_id}` (e.g. `rl:chat:42`). Registered once with `redis.register_script`. https://oneuptime.com/blog/post/2026-03-31-redis-implement-sliding-window-counter-in-redis-lua/view · https://adhdecode.com/articles/rate-limiting/rate-limiting-redis-lua-scripts/
- Return `429` + `Retry-After` on HTTP; on websocket send `{"type":"error","code":"rate_limited","retry_after":n}` and drop the message (don't close).
- Runner-up: `fastapi-limiter` 0.2.0. Why not: adds `pyrate-limiter` as a transitive dep for one function; its identifier is IP+path by default and must be replaced anyway.

## 4. Feature flags

**Pick: self-built `feature_flags` table + `is_feature_enabled(flag, user) -> bool`.**
- Python-native libraries are dead or heavy: `flipper-client` last release 1.3.2 (2023-04-20). `openfeature-sdk` 0.10.0 (2026-06-01) is alive but is only an API shim; you still need a provider (flagd, GO Feature Flag, Unleash — each a separate service or a Postgres deployment). For one VPS with "admin dashboard toggles", a table is the provider. https://libraries.io/pypi/flipper-client · https://libraries.io/pypi/openfeature-sdk · https://gofeatureflag.org/blog/best-opensource-feature-flag-tools
- Schema (two tables, no JSON blobs to grep):
  ```
  feature_flags(key TEXT PK, enabled BOOL NOT NULL DEFAULT false, description TEXT, updated_at, updated_by)
  feature_flag_overrides(id PK, flag_key FK, role_id FK NULL, user_id FK NULL, enabled BOOL NOT NULL,
                         CHECK ((role_id IS NULL) <> (user_id IS NULL)), UNIQUE(flag_key, role_id, user_id))
  ```
- Resolution: user override > any role override (true wins) > global. One query with two LEFT JOINs, or three cheap PK lookups. Cache in-process for 5 s (`cachetools.TTLCache` or a dict+timestamp) and publish `flags_changed` on Redis so other workers drop cache; the dashboard toggle writes the row and publishes.
- Same table doubles as the home for `MAX_CONCURRENT_GAMES`-style runtime settings if you add a `value TEXT` column — or keep a sibling `runtime_settings(key, value)`; don't merge bools and ints into one column type.
- Runner-up: `openfeature-sdk` + in-memory provider fed from the table. Why not: extra abstraction layer over a function that returns a bool; only worth it if a hosted flag service is ever adopted.

## 5. Join queue / waiting room

**Pick: Redis sorted set per queue, score = enqueue timestamp (ms) + Lua for atomic pop/offer, offer held in a TTL key, re-queue on expiry.**
- Sorted set beats list: `ZRANK` gives O(log N) position for the "you are #3" feedback; `ZREM` lets a user leave from the middle; `ZADD NX` makes join idempotent; `ZPOPMIN` is FIFO on timestamp. Lists give none of that without O(N) scans. Streams are the wrong shape (append-only, no rank, no cancel). https://oneuptime.com/blog/post/2026-01-21-redis-priority-queues-sorted-sets/view · https://kommradhomer.medium.com/redis-sorted-set-as-a-unique-fifo-queue-b21c2c5283c6
- Keys: `queue:{room_id}` (ZSET user_id -> ts) for per-room seat waits; `queue:global` for the `MAX_CONCURRENT_GAMES` cap. Offer: `offer:{room_id}:{user_id}` = seat, `EX 30 NX`. Ticketing systems do exactly this (`SET seat:{id} {user} EX 600 NX`), then a sweeper reclaims expired holds. https://medium.com/@sauravsinha_85458/how-to-design-a-virtual-waiting-queue-for-high-demand-ticketing-like-taylor-swift-concerts-b9ea6a1d363a · https://www.hellointerview.com/learn/system-design/problem-breakdowns/ticketmaster
- Flow: seat frees -> Lua `ZPOPMIN queue + SET offer NX EX 30` atomically -> publish `seat_offer` on the room's Redis stream -> websocket pushes to that user -> they `accept` (server `GETDEL offer`, takes seat) or timer runs out. Expiry: don't rely on keyspace notifications (off by default, at-most-once); instead every 5 s a single worker (Redis `SET lock NX` leader) scans `offer:*` via `SCAN` — or better, keep `offers:{room_id}` ZSET scored by deadline and `ZRANGEBYSCORE -inf now` — and for each expired offer: `ZREM` it, re-add the user to `queue:{room_id}` with **original** score (keeps fairness, they lose nothing but the missed offer), decrement their `misses`, drop them after 2 misses, and offer the seat to the next in line. https://redis.io/docs/latest/develop/use-cases/job-queue/
- Position feedback: on every dequeue/leave publish `queue_update {room_id}`; each connected waiter's worker does `ZRANK` and pushes `{position, length}`. Cheap; no per-second polling.
- Fairness: pure FIFO by timestamp is "fair" for this scale. Don't build per-user round-robin (fairque) — one seat per user per room is enforced by `ZADD NX`.
- Runner-up: Postgres table `join_queue(room_id, user_id, enqueued_at, offer_expires_at)` with `SELECT ... FOR UPDATE SKIP LOCKED`. Why not: same logic, but Redis is already hot on the same path (event bus), and the queue is ephemeral state that should not survive a restart anyway (DECISIONS §12: Redis never source of truth for *game* state — queue is not game state).

## 6. Prometheus

**Pick: `prometheus-client` + `prometheus-fastapi-instrumentator` 8.1.0 (2026-07-26), `expose(app)` at `/metrics`.**
- Instrumentator is alive (Python 3.10–3.14, ISC), two-line setup, gives request count/duration/size by handler; you add custom `Counter`/`Gauge`/`Histogram` from `prometheus_client` for games, agent turns, model swaps (§13), queue depth. https://pypi.org/project/prometheus-fastapi-instrumentator/ · https://github.com/trallnag/prometheus-fastapi-instrumentator
- OpenTelemetry metrics + `opentelemetry-exporter-prometheus` works with no collector (`PrometheusMetricReader` + `start_http_server`) but renames metrics (`hvac.on` -> `hvac_on_seconds_total`), adds SDK/MeterProvider ceremony, and its exporter "is not designed to operate in multiprocessing environments". Only worth it when traces to a collector are in scope; §14 says stdlib logging + wide events, so no. https://opentelemetry.io/docs/compatibility/prometheus/client-libraries/ · https://opentelemetry-python.readthedocs.io/en/latest/exporter/prometheus/prometheus.html
- Multi-worker caveat (§8): with `--workers N`, set `PROMETHEUS_MULTIPROC_DIR` from the start script and use `MultiProcessCollector`; gauges need `multiprocess_mode` chosen (`livesum` for connections), `Info`/`Enum` metrics don't work. Instrumentator supports this. Simplest: run **one** worker until measurement says otherwise. https://prometheus.github.io/client_python/multiprocess/
- Runner-up: OTel SDK. Why not: no collector, no tracing, naming translation, multiprocess unsupported.

## 7. Frontend

**Pick: SvelteKit 2 + Svelte 5 (5.56.x, September 2026) in SPA mode via `@sveltejs/adapter-static` with `fallback: 'index.html'`, TypeScript, Tailwind, shadcn-svelte for admin widgets.**
- Fit: runes (`$state`) make a websocket-fed store trivial — one `game.svelte.ts` module holding `$state` of the table; every component that reads `game.seats[i]` re-renders on mutation, no reducers/selectors/immer. Click-any-seat focus = `$state focusedSeat` + a `$derived` view. https://svelte.dev/blog/whats-new-in-svelte-september-2026 · https://svelte.dev/docs/svelte/v5-migration-guide
- Build/serve: `adapter-static` emits a plain `build/` dir; Caddy `file_server` + `try_files {path} /index.html`, or FastAPI `StaticFiles(html=True)` mounted last. No Node at runtime. https://www.npmjs.com/package/@sveltejs/adapter-static · https://blog.siddjain.com/2026/04/11/sveltekit-spa-vs-ssg/
- Weight/perf: smallest bundles and flat memory under sustained websocket updates in 2026 comparisons; matters for a live-log-tail admin page. https://svar.dev/blog/react-vs-vue-vs-svelte-for-modern-web-apps/ · https://byteiota.com/react-19-vs-vue-3-6-vs-svelte-5-2026-framework-convergence/
- Components: shadcn-svelte is runes-native (dialogs, dropdowns, tables, switches — enough for the room-creation form and admin toggles). https://fullstacksveltekit.com/blog/shadcn-svelte-sveltekit
- Runner-up: React 19 + Vite + TS. Why not: same serving story, larger ecosystem, but websocket-driven state needs a store lib (zustand) and memo discipline; slower to build for one developer, bigger bundle. Vue 3.5 + Vite is a near-tie with Svelte (Pinia + `ref`); pick it only if you already know Vue. HTMX 4 (4.0.0 released 2026-08-28, `hx-ws` extension) + Alpine is great for the admin CRUD pages but a card table with per-seat focus, animations and reasoning streams is client-state-heavy — HTML-swapping over the websocket fights that. https://four.htmx.org/announcements/2026-08-28-htmx-4.0.0-is-released · https://four.htmx.org/extensions/hx-ws

## 8. Websocket auth + multi-worker specifics (FastAPI/uvicorn 0.52.4, 2026-08-19)

- **Implementation:** uvicorn `--ws auto` now selects `websockets-sansio` (since 0.35, June 2025); legacy `websockets` impl is deprecated. Don't pin `--ws websockets`. https://uvicorn.dev/release-notes/ · https://github.com/Kludex/uvicorn/pull/2540
- **Workers:** each worker has its own memory; in-process `ConnectionManager` broadcast silently misses clients on other workers. Fan-out must go through Redis (already the event bus: each worker XREADs room streams and forwards to its local sockets). Websocket connections are sticky to a worker for their lifetime by nature; no sticky-session LB config needed on one box. Start with `--workers 1`; the LLM scheduler (§13) is the bottleneck, not the ASGI loop. https://dev.to/kaushikcoderpy/fastapi-websockets-async-connections-scaling-the-multi-worker-nightmare-2026-3346 · https://oneuptime.com/blog/post/2026-01-25-websocket-servers-fastapi-redis/view
- **Keepalive:** uvicorn defaults `--ws-ping-interval 20 --ws-ping-timeout 20` (protocol-level ping/pong, browsers answer automatically). Keep defaults; a client that blocks >20 s gets `1006`. Add an app-level `{"type":"ping"}` every 25–30 s from the client only if a proxy idles sockets (Caddy default idle is fine). Setting interval to 0 via CLI is a known footgun — use `None` in code if you ever disable it. https://www.uvicorn.org/settings/ · https://github.com/Kludex/uvicorn/discussions/1660 · https://github.com/encode/starlette/discussions/2383
- **Max message size:** uvicorn `--ws-max-size` default 16 MiB, `--ws-max-queue` 32. Set `--ws-max-size 65536` (64 KiB): moves and chat are tiny; anything bigger is abuse. Also validate with pydantic on receive and reject with an error frame, not a close.
- **Backpressure:** one slow spectator must not stall a room. Per-connection bounded `asyncio.Queue(maxsize=256)` + sender task; on full, close `4008` (slow consumer). Never `await ws.send_json` inside the fan-out loop.
- **Close codes the frontend acts on:** use private range 4000–4999 (MDN: application use, unregistered). Suggested map: `4001` auth required/expired -> refresh + reconnect; `4003` forbidden (no permission for subscription) -> show error, don't retry; `4004` room not found/finished -> go to lobby; `4008` slow consumer / rate abuse -> backoff reconnect; `4009` server shutdown / worker restart -> reconnect with jitter; `1011` internal error. Starlette `await ws.close(code=4001, reason="token_expired")`; browser reads `event.code`/`event.reason`. Send an explicit `{"type":"close","code":...}` frame *before* `close()` when you need structured payload — `reason` is limited to 123 bytes. https://developer.mozilla.org/en-US/docs/Web/API/CloseEvent/code
- **Lifecycle:** wrap the receive loop in `try/except WebSocketDisconnect`; on disconnect unsubscribe from Redis and remove from queue-position pushes. Auth before `accept()` is impossible for first-message auth, so `accept()`, auth with 5 s timeout, then subscribe. https://fastapi.tiangolo.com/advanced/websockets/
